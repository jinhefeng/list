# 吃吃喝喝 — 营养系统 V2（开发分支）

## 目标与交互边界

1. 对没有品牌官方营养表的饮品和菜品，提供带明确标记、假设和粗略数值的离线估算，不再以“0”或空白假装完整数据。
2. 精确匹配来源数据优先；粗估不能覆盖与当前杯型、甜度、温度、冰量完全匹配的正式营养规格。
3. 内置营养数据随 App 发行；在线更新是可选增强，**离线仍可记录并计算**。
4. 配置完整并启用后，菜品识别和饮品补估入口按当前记录的数据状态显示。可在“更多”配置 AI 模型。
5. 用户点击 AI 操作后，资料直接发给已配置的 HTTPS 服务。附带照片时，App 会重新编码成去除 EXIF/GPS 的 JPEG。API Key 存放在本机钥匙串。

## 在线营养数据包

在「更多 → 营养数据库」填写静态 HTTPS JSON 地址，点击「检查并更新营养数据」。

```json
{
  "schemaVersion": 1,
  "version": "2026.11.14.1",
  "generatedAt": "2026-11-14",
  "entries": [
    {
      "id": "brand.product.variant",
      "nutritionPerUnit": {
        "amount": 100,
        "unit": "ml",
        "energyKcal": 42,
        "sugarG": 7,
        "caffeineMg": 20,
        "proteinG": 1.2,
        "fatG": 0.8,
        "carbohydrateG": 8,
        "sourceType": "estimated",
        "source": "仅作数据结构演示；请替换为真实来源",
        "updatedAt": "2026-11-14"
      }
    }
  ]
}
```

**上述数值仅为格式演示，不是任何品牌的真实营养数据。** 对于远程新增产品，还应提供 `brandID`、`brandName` 和 `name`；新增品牌可通过顶层 `brands` 一起提供。对已有条目按稳定 ID 合并，单个规格由杯型、容量、甜度、温度、冰量和配料构成匹配条件。用户本地覆盖资料优先。

数据包必须使用纯数字分段版本号（如 `2026.11.14.1`），版本须递增；文件上限 5 MB，接口必须为 HTTPS。客户端校验重复 ID、无效数值、缺失的新增产品身份信息、版本回退。验证失败不写入新数据，之前版本继续可用。当前版本仅通过 HTTPS 传输和结构校验；生产开放公共更新前应再采用固定公钥数字签名验证数据包，避免 CDN 或托管账号被盗后的内容篡改。

历史营养快照不被更新自动改写。在线包存入本机独立缓存，不含 API Key，且与个人备份分离；个人已有记录和本地目录修改仍走原先的备份机制。

## 营养来源与估算

- 官方规格：必须对应当前饮品及定制条件；品牌其他杯型的值不能直接标为准确。
- 已录入的每单位营养：在规格确知且没有与甜度不匹配时按容量计算。
- 分类粗估：用于缺少完整资料时。当前为工程初版启发式分类规则，非真实食谱测量；需后续用可信来源校准参数，不应宣称精确。
- 菜品 AI 识别先推断食材和大致克重，再通过本机原料表计算粗估值。已有菜名沿用当前填写；菜名为空时补入识别名称。改名后按新名称重新匹配营养。
- 饮品 AI 补估以整杯为单位，使用已填的品牌、名称和规格。匹配到的目录值按指标保留，AI 只补缺项或离线分类粗估项。AI 数值逐项标记，在表单草稿中随记录保存。

用餐详情展示每道菜的能量、蛋白质、脂肪、碳水和已知糖量。「估算说明」展示来源和假设，记录缺项以短横线显示。旧记录没有逐菜快照时，按菜名提供离线粗估。

## 配置 AI 营养辅助

「更多 → AI 模型设置」使用兼容 OpenAI Chat Completions 的 HTTPS URL、模型 ID 和 API Key。保存配置并开启「启用 AI 营养辅助」。识别菜品或读取饮品营养标签需要模型支持图片理解。

- 生成参数可配置 `max_tokens`、`reasoning_budget`、`stream`、`temperature` 与 `top_p`，默认值为 65536、16384、关闭、0.6、0.95。保存时检查参数范围。
- 点击菜品「AI 识别并估算营养」会立即上传当前照片、菜名与用餐店名。估算自动写入表单草稿，不覆盖已填写的菜名；菜名为空时采用识别名。结果在按钮下展开，约 6 秒后自动收起，可再次展开。
- 点击饮品「AI 补估营养」会立即发送名称、品牌、杯型、容量、甜度、温度和冰量，并默认附带当前饮品照片；没有照片时按文字资料估算。结果自动补入表单草稿，目录和官方数据优先保留，结果同样会短暂展开。
- 识别时在按钮下方只显示最新一条临时状态，包含请求等待时长、流式接收或 NVIDIA 任务轮询进度；状态不写入本机日志或记录。
- NVIDIA 返回 `HTTP 202` 时，使用响应中的 `NVCF-REQID` 轮询 `/status/{requestId}`；流式模式读取 Server-Sent Events。输出被 `max_tokens` 截断或服务商拒绝参数时会给出对应提示。
- 改变饮品名称、品牌或杯型等规格后，按当前规格重新计算。所有 AI 估算只写入未保存的编辑草稿，最终随用户保存记录写入营养快照。

## 验证要点

`cd ios && swift test`。在模拟器和实际设备验证点击即发送、照片是否随请求提交、内联结果自动折叠、失败时草稿保留、饮品按项保留目录值、AI 来源随记录保存，以及关闭 AI 时的离线录入；覆盖流式返回和 NVIDIA `HTTP 202` 轮询。保留对旧记录和旧备份的回归验证。

备注：本开发分支建立在仓库 `main` 的已提交代码上。本地可能未推送的 UI 修改未包含在本分支。
