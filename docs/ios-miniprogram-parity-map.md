## 目标与范围

以微信小程序 `app.json` 注册的九个页面作为功能与数据源参考，逐页复现可见行为、字段、目录内容和页面间跳转。iOS 首发继续作为单人本机应用，启动空白资料库，不导入小程序历史记录或图片。SwiftUI 使用 iOS 原生交互，同时采用小程序已有的品牌色、卡片层级、信息密度和 Logo。

未来多人共同维护清单是架构约束，不是首版功能。首版不增加登录、成员、在线同步、权限配置或用户筛选界面；个人 iCloud Drive 文件夹只承载用户自己选择的备份，不作为多人协作通道。

| 杯型/营养设置 | 全局杯型和容量设置，官方/估算/暂无营养及来源 | 设置独立持久化并纳入用户备份；单位、可空值、估算状态和来源明确，不把缺失值伪装为零 |

## 未来共享清单的架构边界

以下是后续多人协作的准备项，不代表首版要实现或向用户展示：

- 保留已有记录、菜品、照片资产的稳定 UUID；跨页面和备份只传稳定 ID，不依赖数据库行序号。
- 在仓储接口和版本化数据包中留出 `workspaceID`、`authorID`、`createdAt`、`updatedAt`、变更版本与删除标记的扩展位置。尚未决定多人对象是“共同清单”还是“共同记录”；不得现在硬编码成员角色和冲突策略。
- UI 使用用例/仓储边界访问数据，避免把 SwiftData 查询与修改散落在所有页面；首版可由单一本机仓储实现。
- 照片继续作为独立、可寻址资产；以后共享时需另行定义上传、权限撤销、去重、冲突与删除保留策略。
- iCloud Drive 的个人快照不承担实时协作，不推断多人合并，也不把文件同步状态当作记录冲突解决结果。
- 给既有安装保留 SwiftData schema 与备份格式升级路径；“不迁移小程序历史数据”不等于可丢弃已经在 iOS 创建的数据。

## 组件与交付工作包

现有可复用组件：`GanfanCore` 提供记录校验/编码、照片存储、目录探测、快照写入与恢复；`JournalHomeView`、`RecordForms`、`MenuPickerView` 提供可扩展的现有 SwiftUI 流程；`Resources/catalog.json` 是内置目录输入。首轮沿用这些所有者，先提取共享色板、卡片和按钮样式；仅在建立用例边界时再将 UI 直接访问 SwiftData 的部分收敛到单一本机仓储，不因“未来可能多人”提前建立网络层。
