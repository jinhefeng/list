# 菜单目录维护

菜单以“品牌和饮品”为稳定目录，以城市/门店菜单条目记录实际在售款式。一个饮品可以有多条菜单条目，分别对应不同城市或门店；每条都保留来源、核验日期和状态。

## 小程序内维护

首页顶部可打开“饮品清单维护”，按品牌、种类和关键词搜索并单条新增/编辑。页面默认不显示饮品；可搜索、筛选，或点“展示全部饮品”查看全目录；每批最多展示 30 条，可继续加载。维护页可编辑品牌、可选种类、别名、每 100 ml 的含糖量/能量/咖啡因和营养来源，也可停用条目。杯型名称和容量在清单页的“全局杯型与容量”中统一设置，所有饮品共用；记录选择和历史页面只显示杯型名称，容量只用于营养折算。已被记录引用的饮品不允许删除，未被引用的饮品需二次确认后删除。停用只会从记录选择器中隐藏条目，不会删除历史记录。新增条目默认标记为菜单待核验；手工录入不会自动成为已核验菜单。

清单页新录入的通用营养保存在 `nutritionPerUnit`，基准固定为 `amount: 100`、`unit: "ml"`，并包含 `sugarG`、`energyKcal`、`caffeineMg`、`sourceType`、`source` 和 `updatedAt`。记录统计优先匹配精确规格的 `nutritionVariants`；没有匹配数据时，使用记录保存的容量或从全局杯型设置读取容量，再折算每 100 ml 基准。已有旧 `unit: "杯"` 数据只有在旧目录中存在唯一可靠容量时才会换算；多个或未知杯型会作为旧数据保留，未填写新的每 100 ml 数值时不会改动。糖度、温冰选项、营养变体、菜单来源和核验状态均由编辑流程保留。旧目录中的单品杯型字段为兼容性数据，不参与新记录的杯型选择和容量折算。

在饮品记录页创建的自定义饮品会自动保存进当前设备的饮品目录，并关联或创建品牌，因此之后可从常规品牌和饮品选择器中再次选择。记录页营养输入也统一按每 100 ml，写入 `nutritionPerUnit`；营养字段单位只在说明中统一解释一次。记录页不要求填写容量，折算时使用全局设置中的杯型容量。若容量尚未配置，营养基准仍会保存，当前单杯摄入量暂不计算；补齐全局容量后可由目录基准折算。已完成折算的记录保存营养快照，避免目录后续编辑改变旧记录的数值。当前没有配置远程目录地址，这种保存只在本机可用，不会自动同步给其他用户或设备。

CSV 导入模板提供 `drink_category` 和 `nutrition_per_unit_json` 两列，均为可选列，旧 CSV 仍可导入。单位营养 JSON 示例：`{"amount":100,"unit":"ml","sugarG":8.5,"energyKcal":42,"caffeineMg":18,"sourceType":"official","source":"品牌营养表","updatedAt":"2026-10-15"}`。官方营养数据必须填写来源。

## 编辑表格

从 `data/catalog-import-template.csv` 开始，每一行填写一个饮品在某个范围内的一次菜单记录。`city` 和门店字段都留空时表示品牌通用目录；填写城市表示城市级记录；填写门店编号或门店名称表示门店级记录。

- 多个别名、甜度和温冰选项用竖线 `|` 分隔。旧数据中的 `cup_sizes_json` 可继续导入以保留来源信息，但小程序的新记录统一使用清单页的全局杯型配置，不从单品字段读取杯型容量。
- `menu_status` 只能填 `verified`、`pending` 或 `unavailable`。待核验项必须保持 `pending`，不要推测成已在售。
- `source_type` 可填 `official_brand`、`public_menu`、`authorized_platform`、`manual_platform`、`user_report` 或 `pending`。`public_menu` 表示第三方公开菜单汇编，只能保持 `pending`，直到对应饮品在具体门店/城市来源中得到确认。
- 已核验或已确认下架的菜单行需要填写 `checked_at`（`YYYY-MM-DD`）和 `source_name` 或 `source_url`。平台页面人工核验时，可用平台名称、城市和门店作为来源描述。
- `cup_sizes_json` 和 `nutrition_variants_json` 使用 JSON 数组。把整个 CSV 单元格用双引号包起来，并将内部双引号写成两个双引号。营养项可包含 `cupType`、`sizeMl`、`sweetness`、`servingOption`、`energyKcal`、`sugarG`、`caffeineMg`、`sourceType`、`source`、`updatedAt`；营养来源类型仅接受 `official` 或 `estimated`。
- `active` 可留空，默认待核验/在售为 `true`、下架为 `false`。

重复的 `drink_id` 会合并为一个饮品，容量和选项会汇总；不同城市/门店会保留为独立菜单条目。同一饮品在同一范围重复填写会报错。品牌名、饮品名或归属冲突也会报错。

## 生成发布文件

在仓库根目录运行：

```sh
npm run catalog:import -- --input data/catalog-import-template.csv --output data/catalog-release.json --version 2026-10-14.1
```

导入器会在全部行校验通过后才写出文件。不要将空模板生成的文件发布出去。每次发布应更换 `--version`，并将完整的 `catalog-release.json` 替换到静态 HTTPS 托管位置。

## 配置小程序更新

将 `data/catalog-config.js` 的 `remoteUrl` 设为发布文件的 HTTPS 地址，并在微信小程序后台将对应主机加入 `request` 合法域名。响应内容需直接为 `catalog-release.json` 对象，顶层包含 `version`、`generatedAt`、`brands`、`drinks`。

小程序启动时尝试同步目录；记录饮品页也会在打开时接入尚未完成的同步。网络不可用、响应无效或版本相同的时候继续使用本机缓存/内置菜单。成功更新会缓存新版本，并保留本机用户自定义饮品及清单页标记的本机覆盖条目。同步接口不需要、也不应放置平台账户密码或密钥。

`menuEntries` 中的城市和门店信息已进入数据契约；当前记录页使用全局杯型与容量设置，并读取目录中的甜度和温冰选项，尚未按城市筛选菜单。后续城市菜单核验完成后，可在界面增加城市选择并按 `menuEntries` 过滤。

## 当前范围与来源

内置目录目前覆盖 32 个品牌、468 条候选饮品名。其中核心范围是 [2026 新式茶饮连锁前 15](https://ranking.iimedia.cn/ranking/161)、[2026 咖啡连锁前 15](https://www.iimedia.cn/c880/112246.html) 与星巴克；两份榜单没有品牌重叠。另加了杭州城市样本品牌阿嬷手作。来源报告的在售条数、已录入名称数和城市门店证据保存在 `data/catalog-coverage.json` 中，`npm run catalog:coverage` 可查看每个品牌的候选数、来源自报数、已查分页数和缺口状态。

这 468 条**不是完整菜单**，也没有任何一个品牌通过全菜单核验。此次补入一点点官网 2026 年新品公告中的 16 个饮品名、沪上阿姨第三方菜单首页中的 4 个饮品名，以及阿嬷手作杭州限定饮品“桂花酒酿一米”。一点点在官网列出杭州上城、常州天宁、上海黄浦的门店；杭州网也报道了阿嬷手作万象城店在 2026 年 3 月活动期间外卖订单增长。上述线索支持城市样本选取，不证明新品今天仍在售，也不证明特定淘宝闪购门店提供这些饮品。

4 个咖啡品牌尚无可靠的中国大陆现售饮品菜单来源；猫屎咖啡目前仅有广州单店的公开推荐样本，不能代表三城或品牌完整菜单；其余品牌多数只检查了部分公开菜单页或官网产品页。第三方“咖啡奶茶喝什么”说明其信息收集自互联网，计数会变动，部分品牌页还混有餐食。因此它只作为待核验名称线索；来源自报数量不是官方预期数，所有饮品仍保持 `pending`。逐页收录完成前不要宣称品牌菜单已齐。若来源页含冰淇淋、甜品、周边或餐食，应逐项分类，只将饮品写入饮品目录。

门店存在、外卖服务和平台菜单实售是不同层级。官方门店据点只证明品牌在当地列有门店；杭州网报道只证明阿嬷手作门店在一次 2026 年 3 月活动期间外卖订单增长。三城淘宝闪购门店的配送范围和当前饮品菜单仍需逐店核验，`data/catalog-coverage.json` 已将对应状态记录为待核验。用户找不到款式时可在记录流程中创建自定义饮品，先完成记录；当前自定义目录保存在本机，不会自动同步为其他用户的菜单。

首期门店核验范围为杭州上城区、常州天宁区和上海黄浦区的中心城区样本。门店在售状态以淘宝闪购当前页面人工核验为准，必须留存城市、门店、来源描述和核验日期。阿里巴巴集团说明，饿了么于 2025 年 12 月全面焕新为淘宝闪购；旧饿了么 H5 页面和历史接口文档不证明当前淘宝闪购菜单。不要依赖未公开的客户端接口批量采集。公开菜单只补充待核验目录；菜单内容可能变化，需定期复核。
